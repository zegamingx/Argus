# From-Scratch Training Feasibility

**Status:** Research baseline and experiment protocol; no Argus device experiment has been run  
**Last reviewed:** 2026-11-04  
**Phase:** 3 — From-scratch training feasibility  
**Authority:** Evidence and protocol only. No model size, architecture, tokenizer, corpus quota or runtime is selected here.

## 1. Purpose and conclusion

Argus follows Local Knowledge Genesis: each installation constructs and initializes its own model parameters locally. Genesis is not pretraining. A newly initialized model has no acquired language competence merely because its tensors and generation manifest have been committed.

This document evaluates whether subsequent learning can develop useful capability within Android device constraints. It separates published evidence from Argus-specific feasibility, defines E1–E7 experiments, and states what must be measured before architecture and tokenizer decisions.

**Current conclusion:** small-model learning on a deliberately narrow dataset is a valid controlled experiment; mobile DNN training and mobile LLM fine-tuning have empirical evidence; broad general-purpose language-model pretraining from random initialization on Argus target Android devices has not been demonstrated by the sources reviewed here. Argus must not claim feasibility until its own experiments pass on named physical devices.

No Android experiment has been run as part of this documentation review. This document does not authorize implementation, device probing, training, builds, CI execution or artifact publication.

## 2. Evidence categories

| Category | Starting state | What the evidence can establish | What it cannot establish by itself |
|---|---|---|---|
| **A — From-scratch training** | Locally initialized parameters; no pretrained foundation weights | Learning from the initial parameter state on the tested data, model and compute budget | General-language capability or feasibility on a different device |
| **B — Fine-tuning/adaptation** | A previously trained model is present | Cost and feasibility of updating a pretrained or trained model | Capability emerging from random initialization |
| **C — System/runtime optimization** | Depends on the underlying training task | Memory, throughput, energy, thermal, scheduling and recovery techniques | That the model/data/compute combination is feasible or useful |

Do not collapse these into “on-device LLM training.” Every result must identify its category, starting weights, data, device, runtime and workload.

**From scratch** means the model's trainable weights originate from the local Genesis initialization process. LoRA over a frozen pretrained base is fine-tuning even when the adapter itself is newly initialized. **Sustained throughput** means the rate after a measured thermal/performance plateau, not the first cold-start window. An **optimizer update** is one complete parameter update under the declared accumulation and gradient-reduction semantics.

## 3. Research comparison

### 3.1 TinyStories — narrow-domain small-model evidence

[TinyStories](https://arxiv.org/abs/2305.07759) uses synthetic English stories generated by GPT-3.5 and GPT-4, with a deliberately restricted vocabulary and child-oriented story distribution. The paper reports small-model experiments, principally around 1M–35M parameters, and states that the studied small models could be trained on a single V100 GPU in up to 30 hours. It separately evaluates grammar, creativity, consistency and instruction following; its GPT-Eval uses GPT-4 as an external evaluator.

**Supports:** small models can learn useful generation behavior on a deliberately constrained distribution; a narrow fixture is useful for testing whether a training pipeline learns beyond random initialization.

**Does not support:** broad general knowledge, Indonesian/multilingual capability, Android training feasibility, a universal minimum parameter count or an offline-only quality evaluation.

The [TinyStories dataset card](https://huggingface.co/datasets/roneneldan/TinyStories) declares **CDLA-Sharing-1.0**. That metadata is not a completed Argus legal review. Pin an exact revision, retain provenance/notices and complete the corpus-rights review before using or distributing it.

**Argus use:** a pinned, rights-reviewed subset may be considered for E1 as an isolated systems fixture. It is not Argus's general bootstrap corpus.

### 3.2 MELON — mobile DNN memory optimization

[MELON, MobiSys 2022](https://doi.org/10.1145/3498361.3538928) studies memory-constrained on-device DNN training using recomputation, micro-batching, fragmentation handling and adaptive memory budgets. It reports up to 4.33× larger batch size under the same memory budget, 1.89× average (up to 4.01×) throughput improvement at the same batch size, and up to 49.43% energy savings against its tested alternatives.

Those results belong to the paper's evaluated DNN workloads/devices. They are not Argus LLM performance guarantees, proof of from-scratch language training or a universal prerequisite. MELON is a source of memory-management techniques, not an automatic architecture/runtime requirement.

### 3.3 MobileFineTuner — mobile LLM fine-tuning

[MobileFineTuner](https://arxiv.org/abs/2512.08211) describes a native C++ framework for full-parameter and PEFT fine-tuning on physical mobile phones. It studies parameter sharding, gradient accumulation, activation checkpointing, memory-efficient attention and energy-aware scheduling. Its PEFT workflow explicitly loads pretrained LLM parameters.

This is Category B evidence. It supports the feasibility of a mobile-native LLM fine-tuning runtime on the tested devices/configurations, not foundation pretraining from random initialization or universal Android accelerator support.

### 3.4 Smartphone sustained-training study — thermal evidence

[Fine-Tuning a 3B-Parameter LLM on a Smartphone: Characterizing Sustained Training](https://arxiv.org/abs/2610.06325), submitted 2026-10-05, studies LoRA fine-tuning of SmolLM3-3B on an iPhone 17 Pro. The 4-bit base is frozen; the reported configuration uses rank-8 LoRA on query/value projections, batch size 1 and maximum sequence length 1,024.

The paper reports a cold rate near 166 training tokens/s and sustained runs settling around 83–89 tokens/s, roughly half the cold-start rate. The plateau was reached in approximately 32–38 minutes in that workload; tested pause/burst schedules did not restore the sustained rate during the measured run.

This is evidence that cold-start measurements can substantially overstate sustained mobile throughput. It is not full-parameter training, random initialization, Android evidence or a universal 50% penalty. The device, A19 Pro, MLX runtime, iOS scheduler and LoRA configuration are specific to the study.

### 3.5 LiteRT — supported example, not universal training coverage

[Google's LiteRT on-device training guide](https://developers.google.com/edge/litert/conversion/tensorflow/build/ondevice_training) documents separate `train`, `infer`, `save` and `restore` signatures and an Android Java/C++ execution path. Its worked example is Fashion-MNIST image classification.

This demonstrates a documented trainable graph and persistence workflow. It does not prove that arbitrary Transformer, state-space or hybrid models can be trained through LiteRT, or that every required backward operator, precision mode, delegate and optimizer is available on every target device. Argus would need operator coverage and numerical-parity tests before selecting it.

### 3.6 Thermo-FL — thermal-aware federated fine-tuning

[Thermo-FL](https://arxiv.org/abs/2608.21172) uses thermal signals to regulate federated LoRA fine-tuning and sparse update transmission. Its evaluation includes an emulator and a physical testbed with two Jetson Orin Nano clients and a laptop aggregation server.

This supports thermal-aware workload control as a design idea. It is not general smartphone Android validation, from-scratch training or a match for Argus's independent local-instance boundary. Do not copy its temperature values or thresholds into Android policy.

### 3.7 MobiLLM — server-assisted side-tuning

[MobiLLM](https://arxiv.org/abs/2502.20421) moves memory- and compute-intensive backpropagation for a side network to a high-performance server. It is relevant as an example of how server assistance changes resource requirements, but the server participates in training computation.

MobiLLM is excluded from the Argus training baseline. Keeping raw data on-device is not equivalent to local-only training if a server computes part of the training step.

### 3.8 I/O-Cool — unverified claim

The supplied “I/O-Cool” reference and its claimed 90–100% compliance result could not be matched to a verifiable primary paper or authoritative project in this research pass (2026-11-04). Mark it **UNVERIFIED / EXCLUDED**. Do not cite the name, percentage or technique as a fact.

Re-entry requires an exact title, authors, venue/archive identifier, canonical URL and the methodology supporting the claim.

## 5. Android device resource model

A parameter-count estimate or advertised RAM figure is not a training budget.

| Resource | Required evidence | Why it matters |
|---|---|---|
| Model state | Parameter count, loaded representation, precision and bytes | Weights are only one component of training memory |
| Gradients/optimizer | Gradient tensors, optimizer moments, accumulation and update buffers | Full-parameter learning adds substantial state beyond weights |
| Activations | Peak live activations by sequence length, batch/microbatch and layers | Activations can dominate working memory |
| Runtime | Native RSS/PSS, managed heap, workspaces, allocator pools and accelerator allocations when observable | Heap or model-file size alone understates the working set |
| Device headroom | App memory class, process state, current pressure, competing workloads and app budget | Installed physical RAM is not safely available to one process |
| Compute | CPU ISA/sustained performance and verified accelerator runtime, driver, operator and backward support | Peak TOPS or SoC branding is not proof of an executable training path |
| Thermal | Android thermal status/events, initial state, sustained throughput and ambient conditions where measurable | Thermal throttling changes sustained speed and safe scheduling |
| Energy | Battery/charging/power mode, measurement method, joules/update and joules/token where measurable | Useful learning must fit an explicit user energy policy |
| Storage | Corpus/token cache, generations, checkpoints, temporary writes and recovery reserve | Training must not consume space required for atomic recovery/user data |
| Lifecycle | Android version, process importance, background mode, interruptions and restart behavior | A job must recover from process death and OS scheduling |

### 5.1 Memory accounting

Report peak and steady memory for weights, activations, gradients, optimizer state, temporary update buffers, runtime/kernel workspaces, data staging, managed/native process memory and accelerator memory where exposed.

Do not use “model size in FP16” as a proxy for total training RAM. Do not accept a universal threshold such as 70% of installed physical RAM. E3 must use a device-specific app/process budget with explicit OS and user-experience reserve. Android guidance: [Manage your app's memory](https://developer.android.com/topic/performance/memory/manage-app-memory) and [Set app memory budgets](https://developer.android.com/topic/performance/memory/app-memory-budgets).

### 5.2 Thermal and energy telemetry

On Android 10 / API 29 and later, `PowerManager.getCurrentThermalStatus()` and thermal-status listeners provide an OS thermal-status signal. This is not a universal direct SoC-temperature sensor. Record status transitions and correlate them with measured throughput; do not invent a temperature when the platform does not expose one.

If the signal is unavailable or unreliable, mark it unknown and use conservative limits plus sustained measurements. Do not port iOS or Jetson temperature thresholds into Android. Reference: [Android PowerManager API](https://developer.android.com/reference/android/os/PowerManager).

Energy measurements must identify the instrument and accuracy. Prefer calibrated external power measurement for controlled experiments where possible. Battery percentage/current or vendor power counters may be coarse, unavailable or device-specific; treat them as proxies unless calibration is established.

### 5.3 Sustained-performance definition

Record cold-start throughput separately. Continue the fixed workload until a repeatable thermal/performance plateau or a safety stop. Define the plateau before the experiment using moving windows and a tolerance for measurement noise. Report time-to-plateau, plateau throughput, variance, thermal history, memory high-water mark and energy. Record ambient, charging/power and competing workload conditions.

The iPhone study's 32–38 minute plateau is specific to its workload, not a universal Android warm-up interval.

## 6. Experimental controls

Freeze a versioned experiment manifest before running E1–E7:

- Experiment ID, hypothesis, evidence category and predeclared acceptance/stop rules.
- Exact device SKU, SoC, RAM/storage, Android build, driver/runtime, battery and power state.
- Model graph/configuration, parameter count, local initialization algorithm/version, seed and precision.
- Tokenizer/pre-tokenizer revision, vocabulary, special tokens and fingerprint.
- Dataset source/revision/checksum, rights decision, normalization, deduplication, exact split membership and token counts.
- Sequence length, batch/microbatch, gradient accumulation, optimizer/update semantics, schedule, clipping and checkpoint policy.
- Actual execution backend and verified operators.
- Warm-up, measurement windows, repetitions, ambient conditions, energy/memory method and raw result location.
- Code commit and experiment-runtime version.

All comparisons use the same fixture and stated budget. Separate data scaling (fixed model), parameter scaling (fixed token exposure) and compute-matched scaling (matched compute, potentially different token exposure). Runtime comparisons hold mathematical update semantics constant. Use repeated seeds where practical; report variance. Keep training, validation and final test sets disjoint and check for content leakage.

## 7. E1–E7 protocol

The minimal reference architecture is an experimental fixture, not an architecture decision. A successful E1 run proves only that the tested path can learn its constrained fixture.

| Experiment | Controlled setup | Acceptance evidence | Stop conditions |
|---|---|---|---|
| **E1 — Tiny model from scratch** | Locally initialize random weights and train a deliberately small reference language model on a pinned, narrow, rights-reviewed fixture. Freeze tokenizer, splits and optimizer. | Training loss decreases; held-out loss improves; a tiny subset can be overfit; gradients/weights remain finite; samples pass a predeclared basic coherence/consistency rubric. | No meaningful loss trend within the predeclared token/step budget; cannot overfit the subset; repeated non-finite updates or OOM after one bounded adjustment. |
| **E2 — Scaling experiment** | Vary parameters and data exposure in separate sweeps, then run a compute-matched comparison. Fix tokenizer and evaluation split. Repeat seeds where practical. | Reproducible parameter/token/compute trade-off curves; measured resource cost; no hidden budget mismatch or unstable optimization. | No reproducible benefit within the declared budget, unstable optimization, or minimum useful candidate exceeds target-device limits. |
| **E3 — Memory stress** | Measure peak/steady native/process/accelerator memory across sequence, batch/microbatch, activation checkpointing and optimizer choices. Include memory-pressure cases. | Stays under the device-specific app budget with OS headroom; no OOM/LMK or unbounded allocation growth; repeated runs stable. A 1,000-update segment may be an initial screen, then extend to intended session duration. | Repeated OOM/LMK after bounded adaptation; optimizer/activation/runtime memory exceeds the minimum-device budget; fragmentation/leaks prevent safe operation. |
| **E4 — Sustained thermal** | Run a fixed workload from a documented initial state until a measured throughput/thermal plateau or safety stop. Measure cold and sustained rates separately. | Repeatable plateau; sustained throughput above a predeclared minimum useful-progress floor; thermal and memory behavior within the approved envelope. | Rate falls below the floor without safe recovery; severe/critical thermal state or system warning requires pause/stop; device instability. |
| **E5 — Energy efficiency** | Measure idle-adjusted energy for a fixed workload; report joules/update and joules/training token where supported. Compare variants under matched conditions. | Energy fits an explicit session and owner battery budget; uncertainty documented; claimed gains survive matched repetitions. | Exceeds the declared energy budget or measurement cannot distinguish training energy from baseline. |
| **E6 — Recovery/resume** | Inject process death, force-stop, OS reclaim, low storage and interruption around update/checkpoint/cursor publication. Corrupt/truncate checkpoint fixtures. | Last committed model/optimizer/cursor/idempotency state restores consistently; no committed update duplicated or skipped; invalid checkpoints rejected; uncommitted loss bounded by checkpoint cadence. | Any generation/tensor/optimizer/cursor/idempotency mismatch; corrupt checkpoint accepted; committed update duplicated/omitted; last-known-good state overwritten. |
| **E7 — Device comparison** | Run the same manifest on physical devices representing each declared support tier. Include the lowest target tier and a stronger comparison device. | Lowest declared support tier passes E1, E3 and E4; backend/resource differences explained; fallback explicit. If midrange devices are a target, at least one representative midrange Android device must pass. | Only devices above the declared minimum pass; unsupported vendor behavior is required; result cannot be reproduced on a named physical device. |

### 7.1 E2 must not require strict monotonicity

Do not require loss to improve monotonically at every parameter size when token exposure is fixed. Models can be undertrained or data-limited at the tested budget. Report separate parameter-, data- and compute-scaling curves. A simultaneous change in parameters and data cannot identify which factor caused the result.

### 7.2 E3 threshold is device-specific

A 70%-of-installed-RAM rule is not an approved universal threshold. Process budgets/headroom depend on device, process importance and competing workloads. The 1,000-update segment is a proposed initial stress screen, not proof of multi-hour stability.

### 7.3 E4 stop behavior

Use Android thermal status where available and correlate it with throughput. Reduce workload or pause at predeclared status boundaries. Severe/critical status, system warning, unexpected shutdown or unstable operation is a stop condition. Do not use a fixed Celsius limit without device-specific evidence.

### 7.4 E6 correctness bound

The primary requirement is zero loss or duplication of committed optimizer updates. Uncommitted work may be replayed; its bound is the checkpoint interval. A percentage such as 5% of steps is only an operational target and cannot override transactional correctness in [19 — P0 Remediation Design](19_P0_REMEDIATION_DESIGN.md).

## 8. Acceptance and stop policy

Numerical thresholds must be approved only after the target-device matrix, session policy and user battery/thermal expectations are defined. Do not import benchmark values from TinyStories, MELON, iPhone 17 Pro, Thermo-FL or another vendor.

Before declaring feasibility, Argus requires: (1) E1 on a named physical Android device from local random initialization; (2) controlled E2 trade-offs; (3) E3 memory fit for the required session; (4) E4 sustained safe throughput; (5) E5 energy fit; (6) E6 transactional recovery; and (7) E7 evidence on the lowest declared physical target tier. E6 integrity failures, repeated E3 OOM/LMK, unsafe thermal state, non-finite updates, rights/provenance failures or energy-policy violations block progression. A stopped run is recorded as a result, not hidden as success.

## 9. Open questions for Phase 4

No answer is selected here.

1. **Parameter count/capacity:** smallest configuration that is useful beyond E1, and its cost on the lowest target device.
2. **Architecture:** Transformer, state-space/recurrent or hybrid trade-off under equivalent data, tokenizer and compute.
3. **Tokenizer:** multilingual token efficiency versus embedding/output-head memory cost.
4. **Corpus composition/volume:** rights-cleared data mix and feasible token/storage budget; no universal corpus quota is approved.
5. **Data governance:** exact revisions, licenses, attribution and model-training/redistribution rights.
6. **Precision/optimizer:** numerically correct tensor precision, gradients, optimizer state and accumulation semantics.
7. **Checkpoint format:** versioned model/optimizer/RNG/cursor recovery and bounded storage.
8. **Thermal controller:** Android status transitions, throughput signals and safe scheduling across OEMs.
9. **Runtime/backend:** verified forward, backward and optimizer operator coverage on each selected device path.
10. **Useful-learning objective:** measurable general-language outcomes distinct from retrieving stored facts.
